At a ~30 s commit cadence over 29 hours that's ~3,400 retained snapshots, all
within the 120 h retention. Iceberg MERGE INTO walks the current snapshot's

## POC finding — expire_snapshots is BLOCKED on S3 Tables

POC job `000000037h6imf7gsk3` (script `poc_expire_snapshots.py` at
`/Users/deepthid/Desktop/BatterySmart/poc_expire_snapshots.py`, also on S3).

Step (1) `SHOW TABLES IN silver` — OK, both silver tables visible.

Step (2) `CALL \`s3tablescatalog/bs-iot-tables-poc\`.system.expire_snapshots(...)`
failed with:

  pyspark.errors.exceptions.captured.AnalysisException:
    mismatched input '(' expecting STRING

That's a Spark SQL **parser** error — the parser doesn't recognize CALL with a
procedure-style argument list at all, despite
`spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions`
being set in the POC config.

Two hypotheses, same operational conclusion:

  (a) IcebergSparkSessionExtensions aren't wiring through to the
      S3TablesCatalog session (the s3-tables-catalog-for-iceberg-runtime-0.1.8.jar
      bundles its own catalog impl that may not activate extensions), or
  (b) S3 Tables intentionally blocks Iceberg system procedures because it
      provides its own managed maintenance (icebergSnapshotManagement,
      icebergCompaction) and doesn't want callers running both.

Either way: **don't try to drive snapshot expiration from inside the streaming
job on this stack.** Saved to memory as `project-s3tables-call-procedures` for
future sessions. The codepath is in the script behind
`ENABLE_EXPIRE_SNAPSHOTS = False` so it's easy to flip if AWS Support
clarifies later.

This finding STRENGTHENS the AWS Support email — question #4 ("does
expire_snapshots work on managed buckets?") now has empirical evidence. Worth
updating the email with this before sending.
